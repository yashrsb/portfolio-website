# Internationalization (i18n)

## Supported languages
- `en` — English (default, canonical source of truth)
- `hi` — Hindi (UI/content translation layer)

## Libraries
- `i18next`
- `react-i18next`

## Initialization
- Entry: `frontend/src/i18n/index.js`
- Imported once in `frontend/src/main.jsx` before app render.
- Resources are bundled locally:
  - `frontend/src/i18n/locales/en/translation.json`
  - `frontend/src/i18n/locales/hi/translation.json`
- Fallback language: `en`
- Supported languages: `['en', 'hi']`
- Missing/empty translations fall back to English (`returnNull: false`, `returnEmptyString: false`).

## Language detection and persistence
- Storage key: `portfolio-language` (`localStorage`)
- First visit (no saved preference):
  - Browser language starts with `hi` → Hindi
  - Browser language starts with `en` → English
  - Otherwise → English
- Returning visit: saved preference is restored.
- Manual selection takes precedence and is persisted on `languageChanged`.
- `document.documentElement.lang` is updated to the active language.

## UI integration
- Public navigation includes a language switcher (desktop and mobile menu).
- Language changes are instant (no full page reload) and preserve current route/theme state.
- SEO/meta helpers are called with translated titles/descriptions where applicable and update on language change.

## Translation keys and adding translations
- Single default namespace: `translation`
- Key groups: `nav`, `footer`, `common`, page/section groups (`home`, `about`, `experience`, `skills`, `projects`, `projectDetail`, `education`, `contact`, `blog`, `notFound`, etc.)
- To add/edit UI text: update the same key in both `en/translation.json` and `hi/translation.json`.
- Keep technical terms, product/company/project names, URLs, emails, dates, and numeric values unchanged where appropriate.

## Adding a new language
1. Create `frontend/src/i18n/locales/<lang>/translation.json`.
2. Register the resource and language code in `frontend/src/i18n/index.js` (`resources`, `SUPPORTED_LANGUAGES`).
3. Add the language option in `frontend/src/components/navigation/LanguageSwitcher/LanguageSwitcher.jsx`.
4. Extend detection logic if needed for first-visit browser mapping.
5. Verify typography/fallback fonts and run frontend tests/build.

## Dynamic content and fallback behavior
- Existing backend APIs, database records, and admin CRUD flows are unchanged.
- Dynamic portfolio data (projects, experience, education, skills, profile, social links, etc.) continues to come from existing APIs in their original form.
- UI labels/messages are translated; original dynamic content is displayed as-is. If a Hindi-specific field/translation is not available, English/original content remains visible (no blank fallback).
- No backend translation service is used.

## Blog translation handling
- Existing blog data model, admin CRUD, publishing, and API contracts are preserved.
- Blog UI (navigation, filters, metadata labels, actions, empty/error states) is translated.
- Blog post body/title/excerpt/taxonomy content remains the original stored content (English source). Hindi blog translations are **not fabricated** or auto-persisted.
- If a future backward-compatible translation structure is added, the UI can be extended to prefer localized fields with English fallback.

## Limitations
- No separate localized URLs/routes; hreflang alternates are not added because language is preference-based on the same URLs.
- Admin dashboard is not translated in this phase.
- Dynamic database content is not machine-translated; it remains in its original stored language.
